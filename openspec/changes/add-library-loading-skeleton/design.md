## Context

`LibraryView.vue` 目前的載入中畫面（`.assets__empty(v-if="loading && !pagedRealAssets.length && !pendingTasks.length && !showMaterials")`）只顯示 `t('common.loading')` 這行純文字，出現在初次進入 `/library`、切換左側篩選／來源 chip／關鍵字搜尋、翻頁等任何會重打 `GET /images` 的時機。使用者提供 Figma node `1309:7676`（`grid_assets`），透過 Figma MCP `get_design_context` 取得的骨架屏版面：8 張 `skcard_0`～`skcard_7`，每張 252×215、白底、`1px #d2d5dd` 邊框、`10px` 圓角、`4px` 內距、垂直 `8px` 間距，內含縮圖佔位（244×152、`8px` 圓角漸層色塊）、標題佔位（139×13）、一行「標籤膠囊（58×18）＋尺寸文字（64×11）」佔位；漸層色為 `#e4e8f2` → `#f2f5fb`（50%）→ `#e4e8f2`。

`.assets__grid` 既有的 `grid-template-columns: repeat(auto-fill, minmax(12.5rem, 15.75rem))`（200px～252px）跟骨架卡片 252px 寬度相容，可以直接沿用同一個 grid 容器，不需要另外設計版面。

進一步用 `get_design_context` 拉了 `grid_assets` 的父層 `1309:7666`（`panel_assets`，完整面板：工具列＋卡片格線＋頁碼列）才發現，載入中狀態不是只有卡片格線變成骨架屏——工具列（`row_toolbar`：搜尋框、來源篩選 pill、上傳按鈕）整段套用 `opacity: 0.5`，頁碼列（`row_pagination`）套用 `opacity: 0.4` 且左側文字從「共 N 筆素材」換成「載入中…」，右側頁碼按鈕（`‹ 1 2 3 … 16 ›`）維持顯示、只是變淡——這是設計稿畫的示意頁碼，不是真的分頁狀態（見下方決策 4）。

## Goals / Non-Goals

**Goals:**

- 素材清單載入中時，畫面顯示對齊 Figma 的骨架卡片版面（8 張，跟 `PAGE_SIZE` 一致），取代純文字提示
- 骨架卡片外觀、尺寸、漸層色一律取自 Figma `1309:7676` 的實際數值，不用「看起來差不多」的既有變數頂替
- 工具列與頁碼列在載入中一併呈現對齊 Figma `1309:7666` 的降透明度效果，不是只有卡片格線變化，讓整個 `panel_assets` 面板在載入中的視覺一致

**Non-Goals:**

- 不處理圖庫頁以外的載入中畫面（生成任務、AI 試穿等各自獨立）
- 不改動資料載入的時機或 API 呼叫邏輯，純粹是 `loading` 為真時的視覺呈現
- 不做成可重用的獨立元件——目前只有圖庫頁這一處用得到，抽元件是不必要的間接層；若之後有第二個地方需要同樣的骨架卡片，屆時再評估抽取
- 不虛構假的頁碼數字——Figma 頁碼列畫的「1 2 3 … 16」是示意用的固定 mockup 文字，不是真實資料；載入中頁碼列右側維持顯示目前已知的分頁按鈕狀態（沿用既有 `pageItems`），不是照抄設計稿那組固定數字

## Decisions

### 決策 1：骨架卡片直接寫在 LibraryView.vue，不抽成獨立元件

跟 `AssetCard.vue`（會被抽成獨立元件，是因為圖庫頁與「從圖庫選擇」彈窗等多處共用）不同，骨架卡片目前只有圖庫頁載入中這一個使用場景。抽成元件只會多一層 props 傳遞（例如要不要顯示 checkbox 佔位、卡片張數）卻沒有實際重用需求，先直接寫在 `LibraryView.vue` 的 template 與 `<style>` 裡，沿用專案「只有一個使用場景時不預先抽象」的既有慣例（前一個 change `fix-brand-settings-save-toast` 的決策 1 也是同樣的判斷）。

### 決策 2：骨架卡片張數固定 8 張，等於 `PAGE_SIZE`

Figma 設計稿本身畫了 8 張（`skcard_0`～`skcard_7`），跟 `LibraryView.vue` 既有的 `const PAGE_SIZE = 8`（第 400 行）完全一致——每頁本來就顯示 8 筆素材，載入中顯示同樣數量的骨架卡片，讓畫面在「載入中」與「載入完成」兩個狀態之間的版面高度／捲動位置盡量不跳動。不做成依實際視窗寬度動態計算張數（那需要量測容器寬度，複雜度不成比例）。

### 決策 3：漸層色塊加上由左至右的 shimmer 掃光動畫

Figma 是靜態設計工具，沒有、也無法標註動畫時序——畫出的線性漸層本身就是「這裡應該要有骨架屏動態感」的視覺慣例線索（業界骨架屏元件幾乎都會讓漸層左右掃動表示載入中）。純靜態的漸層色塊在視覺上容易被誤認成「壞掉的灰色方塊」而不是「載入中」的訊號。

做法：色塊背景改用比實際區塊寬兩倍的漸層（`background-size: 200% 100%`），用 `@keyframes` 讓 `background-position` 從 `200% 0` 掃到 `-200% 0`，比照專案既有 `@keyframes editorSpin`／`spin` 的寫法慣例（純 CSS animation，不用額外函式庫）。動畫時長取 `1.5s`、`ease-in-out`、`infinite`——這個時長沒有 Figma 依據（靜態稿無法標註），是延伸設計意圖的實作選擇，比照專案裡其他「Figma 沒定義、依討論結果決定」的做法（例如 `fix-mv09-crop-locked-resize` 的比例縮放邏輯）記錄在這裡，供之後回頭調整。

### 決策 4：頁碼列在載入中維持顯示（降透明度），不是完全隱藏；不虛構頁碼數字

現有邏輯是 `.pagination(v-if="displayTotal")`——`displayTotal` 在載入中是 0（還沒有資料），所以頁碼列目前整段不會出現。Figma `1309:7666` 的 `row_pagination` 在載入中反而是「維持顯示、降到 40% 透明度」，左側「共 N 筆素材」換成「載入中…」，跟工具列的降透明度處理手法一致（表達「這塊區域暫時不能互動，但版面結構還在」，而不是讓內容整個消失造成版面跳動）。

做法：新增一個 `showLoadingPanelChrome`（或類似命名）的判斷條件，涵蓋「目前處於骨架屏載入狀態」，讓工具列與頁碼列在這個狀態下套用 `opacity: 0.5` / `0.4` 並用 `pointer-events: none` 停用互動；頁碼列左側文字在這個狀態下改顯示 `t('common.loading')`。

右側頁碼按鈕**不虛構** Figma 畫的「1 2 3 … 16」這組示意數字——那是設計稿的 mockup 內容，跟載入中當下（總頁數還未知）的真實狀態無關。維持顯示既有的 `pageItems` 計算結果（例如切換篩選前殘留的頁碼狀態，或首次載入時只有「1」）並停用點擊，而不是塞入設計稿裡那組固定假數字。理由：頁碼是可被螢幕報讀器讀出的實際資訊，塞入假頁數會誤導使用者以為系統已經知道總頁數；純視覺的降透明度效果已經足夠傳達「這裡正在載入」，不需要犧牲資料正確性去追求跟設計稿像素級一致的假文字。

## Implementation Contract

**行為**：使用者進入 `/library`、或變更左側篩選／來源 chip／關鍵字搜尋／頁碼，只要 `loading` 為真且目前沒有已顯示的素材（`!pagedRealAssets.length && !pendingTasks.length && !showMaterials`，沿用既有判斷條件，以下稱這個條件為「骨架屏狀態」），畫面顯示：

1. 8 張骨架卡片（取代原本的「載入中…」文字），版面套用 `.assets__grid` 既有的 grid 容器
2. 工具列（`.assets__toolbar`）套用 `opacity: 0.5` 並停用互動（`pointer-events: none`）
3. 頁碼列（`.pagination`）**改成骨架屏狀態時也顯示**（不再只看 `displayTotal` 是否為真），套用 `opacity: 0.4` 並停用互動；左側文字從「共 N 筆素材」換成「載入中…」；右側頁碼按鈕沿用既有 `pageItems`／`page` 計算結果原樣顯示（首次載入時 `total` 預設 0、`totalPages` 算出來是 1，會顯示「‹ 1 ›」；篩選切換造成的重新載入則會顯示切換前殘留的頁碼狀態，因為 `total` 只在 API 回應成功時才更新，中途不會被重置成 0）——**不套用 Figma 畫面上那組「1 2 3 … 16」的固定示意數字**

資料回來後（`loading` 變假，或有素材／pending 任務／內建素材可顯示）骨架卡片消失，換成實際的 `AssetCard`／pending 卡片／內建素材清單；工具列與頁碼列的透明度、互動狀態、文字都恢復正常。

**資料形狀**：骨架卡片是純展示用的 template 迴圈（`v-for="n in 8"`），不對應任何實際資料模型，不讀取、不寫入任何 store 或 API 回應欄位。工具列／頁碼列的降透明度狀態是一個衍生自既有 `loading`／`pagedRealAssets`／`pendingTasks`／`showMaterials` 的 computed boolean，不新增任何 store 狀態。

**失敗模式**：`loading` 永遠會在 `useAssets.ts` 的 `load()` 的 `finally` 區塊被設回 `false`（既有邏輯，這次不動），所以骨架卡片不會因為 API 失敗而卡住不消失；API 失敗時既有的錯誤處理路徑（`batchError` 等）維持不變，這次不處理。

**驗收標準**：
- 手動驗證：開啟 `/library`，重新整理頁面時應看到 8 張骨架卡片（白底、灰藍漸層色塊、含掃光動畫）、工具列降透明度且無法點擊、頁碼列降透明度顯示「載入中…」＋「‹ 1 ›」；資料回來後三者都恢復正常
- 切換左側「系統分類」或搜尋關鍵字，重新查詢期間應再次看到骨架卡片＋降透明度的工具列／頁碼列（頁碼列這時顯示切換前的頁碼狀態，不是重置成「1」）
- 骨架卡片版面（尺寸、圓角、間距、顏色）與 Figma node `1309:7676` 逐項比對一致；工具列／頁碼列的透明度數值與 Figma node `1309:7666` 一致（`0.5`／`0.4`）
- 確認頁碼列在骨架屏狀態下不會出現 Figma mockup 裡那組固定的「1 2 3 … 16」字樣（除非剛好使用者原本就在瀏覽第 16 頁附近、恰巧算出一樣的數字）
- `npm run lint` 與 `npx vue-tsc --noEmit` 通過
- 既有圖庫相關測試（若有）維持全過；這次改動不影響 `useAssets.ts`／`api` 層，預期不需要新增測試

**範圍邊界**：僅限 `src/views/LibraryView.vue`（新增骨架卡片 template 區塊與對應 `<style>`，修改 `.assets__empty` 載入中分支的判斷式，工具列與頁碼列新增降透明度狀態）。不修改 `useAssets.ts`、`api/real.ts`、`AssetCard.vue`，也不影響圖庫頁以外的任何畫面。

## Risks / Trade-offs

- [風險] shimmer 動畫時長（1.5s）是猜測值，不是 Figma 標註值，可能跟設計師實際想要的節奏不同 → [緩解] 這個數值容易事後調整（純 CSS 常數），不影響版面結構；已在決策 3 記錄「這是延伸設計意圖的實作選擇」，方便之後回頭校正
- [風險] 骨架卡片直接寫在 `LibraryView.vue`（決策 1），如果之後圖庫以外的頁面也需要類似骨架屏，會需要重構抽成共用元件 → [緩解] 目前只有一個使用場景，抽象化的重構成本留到真的出現第二個使用場景時再付
- [風險] 決策 4 不套用 Figma 畫的固定示意頁碼，視覺上跟設計稿不會逐像素一致（設計稿看起來像是「已經知道有 16 頁」，實作看起來像是「還停在切換前的頁碼」）→ [緩解] 這是刻意的取捨，不製造假資訊比像素級還原更重要；已在 Non-Goals／決策 4 記錄理由，方便設計端日後對照
