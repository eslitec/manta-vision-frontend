## Context

`LibraryView.vue` 目前的載入中畫面（`.assets__empty(v-if="loading && !pagedRealAssets.length && !pendingTasks.length && !showMaterials")`）只顯示 `t('common.loading')` 這行純文字，出現在初次進入 `/library`、切換左側篩選／來源 chip／關鍵字搜尋、翻頁等任何會重打 `GET /images` 的時機。使用者提供 Figma node `1309:7676`（`grid_assets`），透過 Figma MCP `get_design_context` 取得的骨架屏版面：8 張 `skcard_0`～`skcard_7`，每張 252×215、白底、`1px #d2d5dd` 邊框、`10px` 圓角、`4px` 內距、垂直 `8px` 間距，內含縮圖佔位（244×152、`8px` 圓角漸層色塊）、標題佔位（139×13）、一行「標籤膠囊（58×18）＋尺寸文字（64×11）」佔位；漸層色為 `#e4e8f2` → `#f2f5fb`（50%）→ `#e4e8f2`。

`.assets__grid` 既有的 `grid-template-columns: repeat(auto-fill, minmax(12.5rem, 15.75rem))`（200px～252px）跟骨架卡片 252px 寬度相容，可以直接沿用同一個 grid 容器，不需要另外設計版面。

進一步用 `get_design_context` 拉了 `grid_assets` 的父層 `1309:7666`（`panel_assets`，完整面板：工具列＋卡片格線＋頁碼列）才發現，載入中狀態不是只有卡片格線變成骨架屏——工具列（`row_toolbar`：搜尋框、來源篩選 pill、上傳按鈕）整段套用 `opacity: 0.5`，頁碼列（`row_pagination`）套用 `opacity: 0.4` 且左側文字從「共 N 筆素材」換成「載入中…」，右側頁碼按鈕（`‹ 1 2 3 … 16 ›`）維持顯示、只是變淡——這是設計稿畫的示意頁碼，不是真的分頁狀態（見下方決策 4）。

## Goals / Non-Goals

**Goals:**

- 素材清單載入中時，畫面顯示對齊 Figma 的骨架卡片版面（8 張，跟 `PAGE_SIZE` 一致），取代純文字提示
- 骨架卡片外觀、尺寸、漸層色一律取自 Figma `1309:7676` 的實際數值，不用「看起來差不多」的既有變數頂替
- 工具列與頁碼列在載入中一併呈現對齊 Figma `1309:7666` 的降透明度效果，不是只有卡片格線變化，讓整個 `panel_assets` 面板在載入中的視覺一致

**Non-Goals:**

- 不處理圖庫頁以外的載入中畫面（生成任務、AI 試穿等各自獨立）
- 不改動資料載入的時機或 API 呼叫邏輯，純粹是 `loading` 為真時的視覺呈現
- 不做成可重用的獨立元件——目前只有圖庫頁這一處用得到，抽元件是不必要的間接層；若之後有第二個地方需要同樣的骨架卡片，屆時再評估抽取
- 不虛構假的頁碼數字——Figma 頁碼列畫的「1 2 3 … 16」是示意用的固定 mockup 文字，不是真實資料；載入中頁碼列右側維持顯示目前已知的分頁按鈕狀態（沿用既有 `pageItems`），不是照抄設計稿那組固定數字

## Decisions

### 決策 1：骨架卡片直接寫在 LibraryView.vue，不抽成獨立元件

跟 `AssetCard.vue`（會被抽成獨立元件，是因為圖庫頁與「從圖庫選擇」彈窗等多處共用）不同，骨架卡片目前只有圖庫頁載入中這一個使用場景。抽成元件只會多一層 props 傳遞（例如要不要顯示 checkbox 佔位、卡片張數）卻沒有實際重用需求，先直接寫在 `LibraryView.vue` 的 template 與 `<style>` 裡，沿用專案「只有一個使用場景時不預先抽象」的既有慣例（前一個 change `fix-brand-settings-save-toast` 的決策 1 也是同樣的判斷）。

### 決策 2：骨架卡片張數固定 8 張，等於 `PAGE_SIZE`

Figma 設計稿本身畫了 8 張（`skcard_0`～`skcard_7`），跟 `LibraryView.vue` 既有的 `const PAGE_SIZE = 8`（第 400 行）完全一致——每頁本來就顯示 8 筆素材，載入中顯示同樣數量的骨架卡片，讓畫面在「載入中」與「載入完成」兩個狀態之間的版面高度／捲動位置盡量不跳動。不做成依實際視窗寬度動態計算張數（那需要量測容器寬度，複雜度不成比例）。

### 決策 3：漸層色塊加上由左至右的 shimmer 掃光動畫

Figma 是靜態設計工具，沒有、也無法標註動畫時序——畫出的線性漸層本身就是「這裡應該要有骨架屏動態感」的視覺慣例線索（業界骨架屏元件幾乎都會讓漸層左右掃動表示載入中）。純靜態的漸層色塊在視覺上容易被誤認成「壞掉的灰色方塊」而不是「載入中」的訊號。

做法：色塊背景改用比實際區塊寬兩倍的漸層（`background-size: 200% 100%`），用 `@keyframes` 讓 `background-position` 從 `200% 0` 掃到 `-200% 0`，比照專案既有 `@keyframes editorSpin`／`spin` 的寫法慣例（純 CSS animation，不用額外函式庫）。動畫時長取 `1.5s`、`ease-in-out`、`infinite`——這個時長沒有 Figma 依據（靜態稿無法標註），是延伸設計意圖的實作選擇，比照專案裡其他「Figma 沒定義、依討論結果決定」的做法（例如 `fix-mv09-crop-locked-resize` 的比例縮放邏輯）記錄在這裡，供之後回頭調整。

### 決策 4：頁碼列在載入中維持顯示（降透明度），不是完全隱藏；不虛構頁碼數字

現有邏輯是 `.pagination(v-if="displayTotal")`——`displayTotal` 在載入中是 0（還沒有資料），所以頁碼列目前整段不會出現。Figma `1309:7666` 的 `row_pagination` 在載入中反而是「維持顯示、降到 40% 透明度」，左側「共 N 筆素材」換成「載入中…」，跟工具列的降透明度處理手法一致（表達「這塊區域暫時不能互動，但版面結構還在」，而不是讓內容整個消失造成版面跳動）。

做法：新增一個 `showLoadingPanelChrome`（或類似命名）的判斷條件，涵蓋「目前處於骨架屏載入狀態」，讓工具列與頁碼列在這個狀態下套用 `opacity: 0.5` / `0.4` 並用 `pointer-events: none` 停用互動；頁碼列左側文字在這個狀態下改顯示 `t('common.loading')`。

右側頁碼按鈕**不虛構** Figma 畫的「1 2 3 … 16」這組示意數字——那是設計稿的 mockup 內容，跟載入中當下（總頁數還未知）的真實狀態無關。維持顯示既有的 `pageItems` 計算結果（例如切換篩選前殘留的頁碼狀態，或首次載入時只有「1」）並停用點擊，而不是塞入設計稿裡那組固定假數字。理由：頁碼是可被螢幕報讀器讀出的實際資訊，塞入假頁數會誤導使用者以為系統已經知道總頁數；純視覺的降透明度效果已經足夠傳達「這裡正在載入」，不需要犧牲資料正確性去追求跟設計稿像素級一致的假文字。

### 決策 5：骨架屏套用最短顯示時間（500ms），避免真實環境下一閃即逝看不到 shimmer 動畫

實測（Playwright poll DOM，真後端帳號，切換篩選觸發重新查詢）：骨架屏從出現到被實際素材卡片取代，全程只維持約 36 毫秒（`firstSeen: 16.9ms`、`lastSeen: 52.7ms`）。這個時間遠短於決策 3 訂的 shimmer 動畫週期（`1.5s`）的 1/40，動畫技術上正確套用（`animationName`／`backgroundPosition` 皆確認持續推進），但使用者感官上完全看不到任何掃光位移，體感等同「沒有動畫」——這正是使用者回報「看不到 loading 動畫效果」的根本原因，不是動畫實作有誤，而是骨架屏本身出現的時間太短。

做法：`showLoadingSkeleton` 從「單純依賴 `loading` 狀態」改成額外疊加一個最短顯示時間的計時器。查詢開始（`loading` 由 false 變 true 的當下）記錄時間戳；當查詢完成（`loading` 由 true 變 false）時，若距離開始時間還不滿 500ms，延後到滿 500ms 才真正把骨架屏切換成實際內容；若查詢本來就花超過 500ms，則維持原行為（資料一回來就立刻切換，不額外拖慢）。500ms 取自「至少讓 1.5s 週期的 shimmer 跑滿 1/3，讓掃光位移肉眼可辨」的經驗值，同樣不是 Figma 標註值（靜態稿本來就無法標註動畫時序），是延伸決策 3 的實作選擇。

不選擇「縮短動畫週期」（例如把 1.5s 改成 300ms）作為替代方案：動畫週期本身沒有問題（是為了讀秒較久的查詢設計的視覺語言），縮短週期只是治標，遇到查詢時間介於 300ms～1.5s 之間時仍然會出現「動畫還沒跑完就被打斷」的半調子觀感；最短顯示時間才是同時解決「太快看不到」與「維持動畫節奏完整」兩個問題的作法。

### 決策 6：非合流檢視（單頁伺服器分頁）翻頁／切換篩選時清空 `assets.value`；合流檢視刻意不清空

使用者實測回報「全部素材」翻到第 2、3、4、5 頁時看不到骨架屏動畫，第一輪用 Playwright 追查後發現：這幾頁完全沒有觸發骨架屏，不是「太快看不到」，是根本沒進入載入中分支。第一輪的假設（清空所有檢視的 `assets.value`）用更詳細的 debug log 實測後發現是**錯誤的診斷**——真正原因跟合流／非合流兩種查詢機制的差異有關，記錄如下以避免之後重蹈覆轍：

- **合流檢視（`mergesMaterials` 為真：全部素材／物件素材／未分類）**：`fetchAllRealAssets` 每次都把使用者圖庫**整批**撈回來（不分頁），前端再用 `pagedRealAssets`／`pagedMaterials` 自行切頁。用 qa_brand_test 帳號實測：內建素材（`materialsForView`）共 32 筆，`PAGE_SIZE = 8`，正好完整鋪滿「全部素材」的第 1～4 頁——切到第 2、3、4 頁時 `showMaterials` 為真（`pagedMaterials.length === 8`），畫面上本來就有東西可以立即顯示，**不觸發骨架屏是正確行為**，不是 bug：這幾頁的內容是已經在本地的內建素材，沒有任何東西在等待網路回應。即使某次翻頁又重打了 `fetchAllRealAssets`（目前程式碼確實每次翻頁都會重打一次，這是另一個獨立的「重複查詢」效能問題，不在這次修正範圍內——見下方不做的事），拿回來的也是同一份完整資料，`assets.value` 舊值本身就是正確答案，不是「過期」的資料。
- **非合流檢視（單頁伺服器分頁：資料夾、`aiGenerate`／`edit`／`video` 分類）**：`useAssets.ts` 的 `load()` 才是每次真的問後端要「這一頁」的新資料，`assets.value` 在 `await` 期間維持切換前那一頁的舊內容不變。這裡的舊資料**才是真正過期、即將被整批替換掉的錯誤內容**——如果使用者停留久一點會看到「畫面還是上一頁的素材」，資料一回來才整批跳成新頁內容，中間完全沒有經過「載入中」的視覺過渡。這個帳號目前所有非合流分類（`AI 生成`／`編輯產物`／`影片`）筆數都是 0、也沒有建立資料夾，沒有多頁真實資料可以直接重現，但从程式碼可以確定：`pagedRealAssets` 在非合流分支就是直接回傳 `assets.value`（`LibraryView.vue` 的 `pagedRealAssets` computed：`if (!mergesMaterials.value) return assets.value`），只要切換前那一頁不是空的，`wouldShowEmptySkeleton` 就會維持 false，骨架屏同樣不會觸發。

做法：只在 `fetchAssets()` 的**非合流分支**（`await load(buildQuery())` 之前）同步執行 `assets.value = []`；合流分支維持原樣、不清空。因為非合流分支的 `assets.value = []` 與 `load()` 內部緊接著同步執行的 `loading.value = true` 屬於同一輪同步程式碼，Vue 會在同一個 tick 套用完才重新渲染，不會有「先閃一下空清單」的中間態。清空後 `wouldShowEmptySkeleton` 才能正確反映「這次查詢還沒有這一頁的資料」，骨架屏在非合流檢視的翻頁／切換篩選情境下才會被正確觸發，再交由決策 5 的最短顯示時間確保觸發後看得見。

不選擇讓合流分支也清空：合流檢視的資料本來就是完整、正確的本地快取，人為清空只會讓使用者在「全部素材」這種每頁都秒開的檢視上，平白多看到一次沒有意義的骨架屏閃爍，是體感上的退步，不是修正。

不選擇改動 `useAssets.ts` 的 `load()`（例如在其中清空 `assets.value`）：`useAssets()` 是共用 composable，圖庫頁與「從圖庫選擇」彈窗等其他呼叫者可能對「查詢期間是否保留舊資料」有不同假設，改動共用邏輯的影響面超出這次骨架屏的修正範圍；只在 `LibraryView.vue` 自己的 `fetchAssets()` 裡清空，影響面精準限定在圖庫頁。

不做的事（記錄但不在這次修正範圍內）：合流檢視每次翻頁都重打一次 `fetchAllRealAssets`、重新整批撈取使用者圖庫，即使資料沒變也一樣送出請求——這是獨立的效能問題（多餘的網路請求），跟骨架屏的視覺正確性無關，這次不修。

### 決策 7：骨架卡片縮圖尺寸改為正方形，覆蓋原本對齊 Figma `1309:7676` 的橫向比例

老闆要求圖庫管理中心的素材縮圖長寬統一（見另一個 change `unify-library-thumbnail-ratio`），`AssetCard.vue` 的真實素材縮圖框（`.assetCard__thumb`）已經從原本對齊 Figma `1309:7676` 的 `244 / 152`（約 1.6:1，偏橫）改成 `1 / 1` 正方形。骨架卡片的縮圖佔位（`.assetSkeleton__thumb`，決策 1 記錄它直接寫在 `LibraryView.vue`、決策 1.4 的驗收標準原本要求逐項對齊 Figma `1309:7676` 的 `244 × 152` 尺寸）如果維持原本的橫向比例不變，載入中顯示的骨架卡片跟資料回來後顯示的正方形實際卡片，兩者外觀尺寸會不一樣，畫面會在「載入中→載入完成」的瞬間出現明顯的版面跳動（卡片高度突然變化），這正是決策 1 一開始想避免的問題（決策 2 也提到骨架卡片張數固定是為了讓「載入中」與「載入完成」兩個狀態的版面高度盡量不跳動，這裡的比例一致是同一個目的的延伸）。

做法：`.assetSkeleton__thumb` 的尺寸從固定 `15.25rem × 9.5rem`（244×152px，橫向）改成正方形 `15.25rem × 15.25rem`，寬度沿用原本的數值不變（跟 `.assetCard__thumb` 在最大格線寬度 `15.75rem` 下、扣掉 `0.25rem` 內距後的實際寬度一致），只有高度改成跟寬度相等。`.assetSkeleton` 卡片外層的總高度（原本 `13.4375rem`，含縮圖、標題、標籤列與間距）需要跟著重新量測調整，確保骨架卡片整體外觀尺寸跟正方形的 `AssetCard.vue` 一致。

這是老闆的正方形要求主動覆蓋原本的 Figma 靜態稿比例，不是實作疏漏——`unify-library-thumbnail-ratio` 的 design.md 決策 1 已經記錄了選擇正方形而非維持橫向比例的完整理由（背景／物件／模特三種素材類別原生比例不同，正方形是裁切幅度最平均的中性選擇）。這裡不重複那份理由，只記錄骨架卡片需要跟著同步調整、以及為什麼——避免之後有人對照 Figma `1309:7676` 發現骨架卡片「跟設計稿不一致」時，誤以為是實作疏漏而想要「修正」回橫向比例。

### 決策 8：翻轉決策 6——合流檢視也一律固定觸發骨架屏，不管資料是否已在本地快取

決策 6 的判斷（合流檢視資料已經整批快取在本地，翻頁不是真的在等待網路回應，SHALL NOT 為了視覺一致性人為插入骨架屏）在邏輯上仍然成立，且已經用 Playwright 實測驗證過（見決策 6 內文與 tasks.md 第 5 節）。但使用者實際使用後，明確要求反過來：不管資料有沒有在本地快取，切換分類或翻頁都要固定閃一下骨架屏，理由是視覺一致性——使用者希望每次切換都有統一的載入中過場動畫，而不是「有時候瞬間切換、有時候有動畫」這種不一致的體感。這是使用者在看過決策 6 的實際行為後做出的產品決策覆蓋，不是決策 6 的推論有錯。

做法（第一版嘗試，經實測發現不夠）：`LibraryView.vue` 的 `fetchAssets()` 不再區分合流／非合流分支決定要不要清空 `assets.value`——兩個分支都在一開始同步執行 `assets.value = []`。合流分支原本「維持原樣不清空」的做法（決策 6 的做法段落）整段廢止；非合流分支既有的清空邏輯不變。

**實測後發現只清空 `assets.value` 不夠**：`showLoadingSkeleton` 的觸發時機（`skeletonHoldActive` 何時被設成 `true`）原本寫在 `watch(loading, ...)` 裡，只有當 `wouldShowEmptySkeleton.value`（`!pagedRealAssets.value.length && !pendingTasks.value.length && !showMaterials.value`）為真時才會開始這次的骨架屏顯示。「全部素材」這類合流檢視翻頁時，即使清空了 `assets.value`，如果目標頁面本來就有內建素材可以顯示（`showMaterials` 為真，例如這個測試帳號的內建素材筆數剛好鋪滿前幾頁），`wouldShowEmptySkeleton` 依然是 false，骨架屏根本不會開始這次的 hold，等於第一版做法在有內建素材的頁面完全沒有效果——用 Playwright 實測「全部素材」連續翻頁確認骨架屏仍然完全沒有出現。

**正確做法**：把「要不要開始這次骨架屏顯示」的判斷，從「目標內容是否為空」（`wouldShowEmptySkeleton`）改成「是否有一次新的查詢正在進行」——只要 `loading` 由 false 變 true，就無條件開始 `skeletonHoldActive`，不再檢查 `wouldShowEmptySkeleton`。`showLoadingSkeleton` 的計算式也同步簡化成 `skeletonHoldActive.value || loading.value`，拿掉原本疊加的 `&& wouldShowEmptySkeleton.value` 條件。`wouldShowEmptySkeleton` 這個 computed 不整個刪除，仍然保留給 `.assets__empty`（查詢完成但確實沒有任何素材時顯示的純文字提示）判斷用；只是不再拿它來決定骨架屏要不要開始顯示。

這樣一來，不管目標頁面／分類最終有沒有內容可以顯示，骨架屏都會在查詢一開始就固定出現，並維持決策 5 的最短顯示時間（500ms），之後才依照查詢完成後的實際資料（`pagedRealAssets`／`pendingTasks`／`showMaterials`）切換成實際內容或「圖庫是空的」文字提示。

不選擇讓合流分支也清空就結束（僅第一版做法）：已經實測證明不夠，記錄在這裡避免之後重蹈覆轍。

這個翻轉的代價（決策 6 原本想避免的問題）：合流檢視（全部素材／物件素材／未分類）翻頁時，即使資料已經整批快取在本地、`fetchAllRealAssets` 其實不需要再打一次網路請求就能秒開，畫面還是會固定延遲到滿 500ms 才顯示，比原本「秒開」的體感慢了將近半秒。這是使用者明確要的取捨（視覺一致性優先於「快就直接顯示」），記錄在這裡供之後回頭檢視。

## Implementation Contract

**行為**：使用者進入 `/library`、或變更左側篩選／來源 chip／關鍵字搜尋／頁碼，只要 `loading` 為真且目前沒有已顯示的素材（`!pagedRealAssets.length && !pendingTasks.length && !showMaterials`，沿用既有判斷條件，以下稱這個條件為「骨架屏狀態」），畫面顯示：

1. 8 張骨架卡片（取代原本的「載入中…」文字），版面套用 `.assets__grid` 既有的 grid 容器
2. 工具列（`.assets__toolbar`）套用 `opacity: 0.5` 並停用互動（`pointer-events: none`）
3. 頁碼列（`.pagination`）**改成骨架屏狀態時也顯示**（不再只看 `displayTotal` 是否為真），套用 `opacity: 0.4` 並停用互動；左側文字從「共 N 筆素材」換成「載入中…」；右側頁碼按鈕沿用既有 `pageItems`／`page` 計算結果原樣顯示（首次載入時 `total` 預設 0、`totalPages` 算出來是 1，會顯示「‹ 1 ›」；篩選切換造成的重新載入則會顯示切換前殘留的頁碼狀態，因為 `total` 只在 API 回應成功時才更新，中途不會被重置成 0）——**不套用 Figma 畫面上那組「1 2 3 … 16」的固定示意數字**

資料回來後（`loading` 變假，或有素材／pending 任務／內建素材可顯示）骨架卡片消失，換成實際的 `AssetCard`／pending 卡片／內建素材清單；工具列與頁碼列的透明度、互動狀態、文字都恢復正常。**（決策 5）**若查詢從開始到完成不滿 500ms，骨架屏延後到滿 500ms 才切換，不是資料一回來就立刻切換；若查詢本來就花超過 500ms，則資料一回來就立刻切換，不額外拖慢。

**資料形狀**：骨架卡片是純展示用的 template 迴圈（`v-for="n in 8"`），不對應任何實際資料模型，不讀取、不寫入任何 store 或 API 回應欄位。工具列／頁碼列的降透明度狀態是一個衍生自既有 `loading`／`pagedRealAssets`／`pendingTasks`／`showMaterials` 的 computed boolean，不新增任何 store 狀態。

**失敗模式**：`loading` 永遠會在 `useAssets.ts` 的 `load()` 的 `finally` 區塊被設回 `false`（既有邏輯，這次不動），所以骨架卡片不會因為 API 失敗而卡住不消失；API 失敗時既有的錯誤處理路徑（`batchError` 等）維持不變，這次不處理。

## Risks / Trade-offs

- [風險] shimmer 動畫時長（1.5s）是猜測值，不是 Figma 標註值，可能跟設計師實際想要的節奏不同 → [緩解] 這個數值容易事後調整（純 CSS 常數），不影響版面結構；已在決策 3 記錄「這是延伸設計意圖的實作選擇」，方便之後回頭校正。**後續發現**：這個猜測值本身沒有錯，但真實後端回應太快（實測骨架屏只顯示約 36ms），使用者根本沒機會看到它跑起來，才是使用者回報「看不到動畫」的實際原因——已透過決策 5 的最短顯示時間解決
- [風險] 決策 5 的最短顯示時間（500ms）同樣是經驗值，不是 Figma 或後端 SLA 依據 → [緩解] 純前端常數，事後可依實際使用回饋調整；抓 500ms 是在「勉強能看到掃光位移」與「不要在資料明明已經到了的情況下人為拖慢畫面」之間取捨
- [風險] 骨架卡片直接寫在 `LibraryView.vue`（決策 1），如果之後圖庫以外的頁面也需要類似骨架屏，會需要重構抽成共用元件 → [緩解] 目前只有一個使用場景，抽象化的重構成本留到真的出現第二個使用場景時再付
- [風險] 決策 4 不套用 Figma 畫的固定示意頁碼，視覺上跟設計稿不會逐像素一致（設計稿看起來像是「已經知道有 16 頁」，實作看起來像是「還停在切換前的頁碼」）→ [緩解] 這是刻意的取捨，不製造假資訊比像素級還原更重要；已在 Non-Goals／決策 4 記錄理由，方便設計端日後對照
